# Lesson: lock-free ring buffer — measuring SPSC against a mutex queue (`lock_free_buffer`)

The library's `Logger` (010-09) gives every thread that logs its own ring buffer, and one consumer thread empties them. Each buffer has one writing thread and one reading thread (SPSC), so two `std::atomic` indices are enough, with no lock. This lesson builds that structure itself as a `SpscRing<T, N>` of about fifty lines and measures it against a queue guarded by a `std::mutex`, each for **a fixed time (300 ms per case)**. Five cases: mutex queue 1:1, SPSC 1:1, SPSC 1:1 with both indices on one cache line (false sharing), 4 producers → one mutex queue, and one SPSC per producer + one consumer (the `Logger`'s layout). Each case checks that every producer's sequence numbers only increase and that nothing was lost (`produced == consumed`). Read the real implementation in [`thread_log_buffer.hpp`](/include/atugcc/core/detail/thread_log_buffer.hpp) and [`ring_buffer.hpp`](/include/atugcc/core/ring_buffer.hpp) in the `uses` tab. Background: [lock_free_logging.en.md](/docs/cpp_evolution/lock_free_logging.en.md).

## Mutex queue and SPSC ring buffer
| | `std::mutex` queue | SPSC ring buffer (`std::atomic`) |
|---|---|---|
| Synchronization | a lock for every push and pop; the other side waits | the producer writes only `tail`, the consumer only `head`; nobody waits |
| Ordering | the lock orders before and after | write the slot, then store `tail` with `release`; a consumer that reads it with `acquire` also sees the slot contents |
| Several producers | works as it is (the lock lines them up) | does not work; one ring per producer, and the consumer reads them in turn |
| Cost | lock contention, sleeping and waking | cache lines passed between cores; false sharing when the indices share a line |

## What to look for
- **The throughput numbers depend on the machine, the load and the build.** Usually SPSC beats the mutex queue, and the false-sharing row is slower than the padded SPSC. If not, look for why (core count, other programs, a Debug build). In particular, the false-sharing row can come out the same as the padded SPSC or even faster (it did in a Release run on 2026-11-04). This simple ring reads the other side's index on every push and pop, so that line moves between the cores anyway, padded or not. Keep a copy of the other index as in exercise 2, and the difference padding makes shows up. With fewer than 5 cores, rows 4 and 5 get `(oversubscribed: N cores)`: there are more threads than cores, so they run by yielding to each other (`yield()`). `verified` must still always be `ok`.
- **`release`/`acquire`**: the producer writes the slot first and publishes it with `indices_.tail.store(tail + 1, std::memory_order_release)`. When the consumer sees that value through `indices_.tail.load(std::memory_order_acquire)`, it also sees every write **before** that store, the slot contents included (happens-before). In the other direction, the consumer's `release` on `head` and the producer's `acquire` pass on "that slot has been read, it may be written again".
- **Indices keep growing and are masked**: `head` and `tail` never wrap to 0; they only grow, and the slot is chosen with `index & (N - 1)` (`N` is a power of two, like `FixedRing` in the lesson `concepts`). So empty is `head == tail` and full is `tail - head == N`. If the indices wrapped from `N` back to 0, the two states would look the same and one slot would have to stay unused.
- **`alignas(64)`**: when `head` and `tail` sit on one cache line (usually 64 bytes), every write by one side invalidates that line on the other core, so two unrelated variables pass the line back and forth (row 3). In the lesson, `Indices<true>` gives each index its own 64-byte line and `Indices<false>` puts both in one 64-byte-aligned line; both fill the spare bytes explicitly, because padding the compiler adds for `alignas` raises MSVC warning C4324 (an error here). The standard `std::hardware_destructive_interference_size` is also 64 on both toolchains, but its value can change with target CPU options, so it is kept out of ABIs and file formats. The library and this lesson use the constant 64.
- **Several producers must not share one SPSC**: two producers that read the same `tail` write the same slot, and one item disappears. The old Logger did exactly that ([KI-025](/docs/known_issues.md): every thread pushed into one single-producer queue). 010-09 changed to a buffer per thread, as in row 5.
- **Find the same lines in the library**: `BufferHeader` in `thread_log_buffer.hpp` holds `writePos` and `readPos`, and in [`thread_log_buffer.cpp`](/src/core/thread_log_buffer.cpp) the producer reads `readPos` with `acquire` and stores `writePos` with `release`, the same pair as this lesson's `tail`/`head`. The library keeps both indices in one 64-byte `BufferHeader`, though, because that header is also the layout of the memory-mapped file (010-10).

## Exercises
1. Make a copy, change every `release` and `acquire` to `std::memory_order_relaxed`, and run it with the `linux-x64-tsan` preset. Where (which slot variable) does ThreadSanitizer report a data race? On x86 the relaxed version may still seem to give correct results; why is it wrong anyway?
2. Instead of the producer reading `head` with `acquire` every time, keep a copy of the last seen `head` on the producer side and read `head` again only when the ring looks full. How does row 2's throughput change?
3. Shrink the buffer size `kCapacity` from 1024 to 8. When the ring is full more often, what happens to each row's throughput? Is `verified` still `ok`?
